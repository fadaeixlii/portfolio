# Decisions

- **2026-09-19 · Own VPS behind Cloudflare, not Vercel.** The box already runs `job` and `outreach`, so the marginal cost is zero and the deploy pattern exists. Cloudflare's free proxy supplies the edge cache, TLS and DDoS protection that a single-region origin cannot. The v1 Cloudflare Pages adapter was never actually installed — that doc was all TODOs.
- **2026-09-19 · Domain `mohammadmkh.dev`.** Matches the GitHub handle. `.dev` is HSTS-preloaded, so HTTPS is not optional.
- **2026-09-19 · Booking window 09:00–18:00 `Asia/Tehran`, Mon–Fri.** 08:00–16:00 would have ended at 13:30 Berlin, making every European afternoon unbookable on a site whose entire job is getting a call booked.
- **2026-09-19 · No `googleapis` package.** Three `fetch` calls replace a ~2 MB dependency.
- **2026-09-19 · Content as typed TS, not MDX.** With the blog cut, MDX earned nothing and cost three dependencies.
- **2026-09-19 · react-bits vendored, not installed.** MIT + Commons Clause; it ships as copy-paste source. Two components under `src/components/motion/` carry attribution headers.
- **2026-09-19 · `<Reveal>` is opt-in per section.** Fade-up on every section is the clearest generated-page tell; the primitive exists so the call is reversible in one place.
- **2026-09-19 · Amber on blue-slate.** Rejects both the template's orange/lime and the near-black + acid-accent AI default.
- **2026-09-19 · `middleware.ts` is `proxy.ts` in Next 16.** Verified in `node_modules/next/dist/docs/01-app/02-guides/upgrading/version-16.md`. A file named `middleware.ts` is silently ignored, so locale routing would never have run.
- **2026-09-19 · No `--radius-*` mapping in `@theme inline`.** Tailwind v4 reserves that namespace, so `--radius-sm: var(--radius-sm)` resolves to itself. Radii are used as arbitrary values, `rounded-[var(--radius-lg)]`, reading Layer 1 directly.
- **2026-09-19 · Pages use React's `use(params)`, not `await params`.** Awaiting makes the component async, where `useTranslations` throws. `use()` keeps it synchronous so `setRequestLocale` and the hook coexist, and the routes stay prerendered.
- **2026-09-19 · `ThemeToggle` uses `useSyncExternalStore` as its mount flag.** The `useState` + `useEffect` pattern trips `react-hooks/set-state-in-effect`; this shape gives identical server and first-client markup, so there is no hydration mismatch.
- **2026-09-19 · Display name is "Mohammad M. Khani".** The formal "Mohammad MohammadKhani" is for formal contexts only. Farsi keeps the natural compound "محمد محمدخانی" because Persian does not use middle initials.
- **2026-09-19 · Reschedule is out of scope; cancel-then-rebook is the flow.** `patchEvent` (event edit/reschedule) was dead code — never called from any route. Deleted rather than kept "for later". A visitor who needs a different slot cancels via the manage link and books again.
- **2026-09-19 · `lighthouserc.json` performance/best-practices/LCP thresholds relaxed from the original 0.95/0.95/2500ms floor to 0.7/0.9/6000ms.** The 0.95 floor was aspirational and never measured against this build: `quality.yml`'s first real run would have been red on every push. Measured on this machine after the Phase 5 fixes (Booker lazy-loaded, home JS split via `LazyMotion`, 45 unreferenced images removed): `/en` performance 82 (LCP 4.8s), `/en/schedule` 79 (LCP 5.1s), `/en/work` 78–79, `/fa` 88, across single and 3-run LHCI samples. Best Practices sits at 96, not 100, because of `errors-in-console` from the CI job's dummy Supabase/Google credentials (real creds fix this; it isn't a code defect). Localhost has no CDN, no HTTP/2 multiplexing and no Cloudflare cache, so LCP here is pessimistic against what the VPS behind Cloudflare will actually serve — but the honest number to gate CI on is the one measured, not the one hoped for. 0.7/0.9/6000ms is a floor this build clears with margin on every observed run; raise it again once a production Lighthouse run (through Cloudflare, HTTP/2, real creds) gives a real number to target instead of a guess.
- **2026-09-19 · Playwright's webServer runs on port 3100, not 3000.** `reuseExistingServer: !process.env.CI` is genuinely useful locally, but on port 3000 it silently adopted *any* server already listening there — a stray `pnpm start`, a stale server a previous run failed to tear down, a dev server someone left running — and tested that instead of building fresh. Two real incidents on this project: a whole page looked like it had broken CSS, and a run passed against code that had already regressed. A dedicated port means reuse can only ever mean "reuse a server this suite itself started." Do not move it back to 3000.
- **2026-09-19 · CI had never once run its own tests.** Every `quality` run since the workflow was written failed in 9–11 seconds at `pnpm/action-setup@v4` with `No pnpm version is specified`, and `deploy` — gated on `workflow_run` success — skipped every time. So the green-looking local suite was the *only* gate this project ever had, and a red push would have deployed nothing rather than warned anyone. Fixed by adding `"packageManager": "pnpm@10.13.1"` to `package.json`, which is where the action looks first and which also pins the version for everyone. A workflow that fails identically on every push trains people to stop reading it; check that CI has actually executed a step you care about, not merely that a run exists.
- **2026-09-19 · Visual baselines are win32-only and CI therefore has no visual-regression coverage.** Playwright keys snapshots by platform; the four `styleguide-*-chromium-win32.png` files were captured on Windows, and the `ubuntu-latest` runner looks for `-chromium-linux.png`, finds nothing, and fails on a *missing baseline* — which reads exactly like a visual regression and is not one. The screenshot tests now `test.skip` off win32. This is a real gap, not a fix: until someone generates Linux baselines on Linux, nothing in CI catches a visual change. Named here rather than left as a silently-skipped test.
- **2026-09-19 · Snapshot tolerance is `maxDiffPixelRatio: 0.0005`, measured rather than guessed.** The previous `0.02` was picked without a number behind it, and it let a site-wide font change through. Swapping the Farsi headings from Archivo to Vazirmatn moves 59,717 pixels on this 1280×4545 page — Playwright's own count, ratio ~0.02, landing exactly on the old threshold. The Farsi pair passed on a visibly wrong render; the English pair failed only because the new body face shifted page height by one pixel, and a dimension mismatch fails outright before any ratio is considered. Had the height held, all four would have gone green. The floor is ~0: two renders of an unchanged page here differ by 0 pixels byte-exact. `0.0005` (~2,900 px) sits an order of magnitude above the noise and twenty times below the smallest real change measured. Pick this number from a measurement of both ends, never from a guess about the middle.
- **2026-09-19 · Three more stale-state traps, all of which produced a false reading on this project in one day.** (1) A leftover `.next/diagnostics/build-diagnostics.json` from a killed build makes the next `next build` refuse with "Another next build process is already running"; it is a stale marker, not a lock — delete the file. (2) Turbopack serves a cached CSS chunk on the dev server, so a change to a design token can appear to do nothing while the compiled CSS still holds the old inlined value; verify token changes against a production build, and `rm -rf .next` when a change should be visible and is not. (3) A readiness `curl` that returns 200 does not prove the server answering is *yours* — a `next start` can lose the port to `EADDRINUSE`, and the probe then passes against someone else's build. Check that your own bind succeeded, not merely that the port answers. Together with `reuseExistingServer`, these four share one shape: a check that confirms a *condition* when what you needed was provenance.
- **2026-09-19 · The booker suite was never hermetic; it rode on live Google credentials.** `booker.spec.ts` mocked `/api/availability` and `/api/book`, and its own header comment claimed the suite was isolated. It was not: `Booker.tsx` fires `/api/health/calendar` once on mount and gates the whole month grid behind the result, and that call was never stubbed. On a machine holding a working refresh token the probe returned 200 and every test passed; CI's dummy credentials got a real `401 invalid_client` from Google, the booker swapped in the email fallback, and all five grid tests failed with `getByRole('table')` not found. Worse, the "503 from availability shows the email fallback" test passed in CI for the wrong reason — it got the fallback from the health probe, not from the availability 503 it exists to cover. The probe is now stubbed per test, the unhealthy path has its own test that keeps availability healthy so it cannot pass by the other route, and the fix was proved by pointing the stub at 503 and confirming exactly those five go red on the intended assertion. The general lesson is the session's fifth instance of one shape: a green suite is evidence about the machine that ran it until every external call it makes is accounted for.
- **2026-09-19 · Lighthouse reports are uploaded as a CI artifact; before this, no run left a number behind.** `lighthouserc.json` had `collect` and `assert` but no `upload`, and the workflow never uploaded `.lighthouseci/`, so every report was written to the runner and discarded with the container. A green Lighthouse step therefore proved only that each category cleared its floor — and the floors are deliberately uneven, so "Lighthouse green" means different things per category: accessibility and SEO pass at a strict 0.95 and are real signal, while performance passes at a relaxed 0.7 against a build that measured 79–82 locally, which is likely a narrow clearance nobody could verify. Now `upload.target: filesystem` plus `actions/upload-artifact` with `if: always()` — `always()` because a *failed* assertion is exactly when the numbers are worth reading, and that is the run where a step-level failure would otherwise skip the upload. Raise the thresholds only against uploaded numbers from a production run through Cloudflare and HTTP/2, never against a guess.
- **2026-09-19 · `include-hidden-files: true` on the Lighthouse artifact upload, and `if-no-files-found: error` rather than `warn`.** The sixth instance of this session's one bug, and the most literal: the upload step was added specifically to stop discarding the reports, ran green, and uploaded nothing. `actions/upload-artifact@v4` defaults `include-hidden-files` to `false`, `.lighthouseci` is dot-prefixed, so every file under it is hidden, the glob matched nothing, and `if-no-files-found: warn` warned and succeeded. The run stayed green with `total_count: 0` artifacts, which is indistinguishable from success unless someone queries the artifacts API — and the LHCI log in the same run says "Dumping 12 reports to disk … Done writing reports to disk", so the files were there the whole time. `warn` is what made it silent, so it is now `error`: a step whose entire purpose is to produce an artifact should fail when it produces none. Note that this caught the person actively watching for it — the plan was always to verify the artifact landed rather than assume the config took, and it had not.
- **2026-09-19 · Lighthouse assertions pin `aggregationMethod: "median"`; the default was asserting against the best run of three.** The first uploaded reports gave this project its first real Lighthouse baseline, and reading them raised a question: `/en` scored 60 on one of three runs against a floor of 70, and `/en/work` hit 6383ms LCP against a 6000ms ceiling, yet the job went green. The answer is in the LHCI config reference: when an assertion sets no `aggregationMethod`, the default is **`optimistic`** — "the value that is most likely to pass from all runs" — not the median. So the gate was reading the single best of three runs, and a route could fail two runs in three and still pass. Now pinned to `median` on every assertion, which the current build clears on all four routes (perf medians 89 / 79 / 77 / 91, LCP medians 3694 / 5366 / 5045 / 3465). `pessimistic` would be stricter still and would redden this build today; `median` is the honest middle and is a real tightening rather than a cosmetic one. Confirmed against the documentation rather than inferred from the data — the empty `assertion-results.json` on a passing run tells you nothing about how the aggregation happened.
- **2026-09-19 · The first real Lighthouse baseline, and why the thresholds are not being raised yet.** Median of 3 runs per URL, with spread, from CI run 35470406451 on `a6ee315`: `/en` perf 89 [60–92], LCP 3694ms [3315–4725]; `/en/schedule` perf 79 [77–79], LCP 5366ms [4997–5376]; `/en/work` perf 77 [76–81], LCP 5045ms [4998–6383]; `/fa` perf 91 [89–92], LCP 3465ms [3313–3764]. Accessibility 98–100, best-practices 96 flat, SEO 100 flat, CLS 0.000 everywhere — those pass strict 0.95 thresholds with room, and `/fa` being the *fastest* route answers any worry that the RTL font switch cost something. The blocker on raising the performance floor is not the level but the **variance**: a 32-point spread on `/en` alone, and the local 79–82 estimate was roughly right about the typical number while being completely silent about it. A CDN and HTTP/2 will move the level; they will not obviously fix a 32-point spread on one route. The weak routes are `/en/work` (16:10 screenshot grid) and `/en/schedule` (booker month grid), both near 5000ms LCP — that is where the work is, not on `/en`.
